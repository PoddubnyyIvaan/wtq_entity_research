# Спецификация: entities.tsv → sample200.jsonl (конвертер формата)

- Тип спецификации: **Pipeline** (преобразование одного файла-источника в канонический
  входной формат пайплайна исследования).
- ID: `entities_to_sample200`
- Статус: утверждена (решения пользователя зафиксированы в разделе «Input»).

## Motivation

Канонический пайплайн исследования (этапы 2/3/6) читает вход из
`samples/sample200.jsonl` (JSONL, 15 ключей, фиксированных в схеме). У пользователя
есть полный список сущностей в другом формате — `samples/entities.tsv`
(TSV: `name`, `type`, `count`, `all_types`). Необходим детерминированный скрипт,
который переводит этот список в формат `sample200.jsonl` без потери строк, чтобы
далее прогнать по нему exp2/exp3 (проверка наличия русского перевода в Википедии).
Потери данных недопустимы: каждая строка TSV → ровно один объект в JSONL.

## Input

### Файл-источник: `samples/entities.tsv`
- Кодировка: UTF-8 (без BOM), переводы строк LF, разделитель полей — TAB.
- **Парсинг: построчный `split("\t")` без CSV-quoting.** В поле `name` встречаются
  двойные кавычки как часть surface form, например `"That Girl" (with Shaggy)`.
  При использовании `csv.DictReader` такие строки интерпретируются как CSV-поля с
  кавычками и **теряются 2 строки** (проверено: 44237 физических строк vs
  44235 строк у csv-парсера). Кавычки являются частью названия и сохраняются.
- Заголовок (первая физическая строка): `name\ttype\tcount\tall_types`.
- Каждая следующая строка — ровно 4 поля:
  | Поле | Тип | Описание |
  |---|---|---|
  | `name` | str | surface form сущности (может содержать `"` и `,`) |
  | `type` | str | основной NER-тип (ORG/GPE/PERSON/PRODUCT/LOC) |
  | `count` | int | частота в исходном датасете (в выход НЕ включается) |
  | `all_types` | str | NER-теги через `|`, напр. `PERSON|WORK_OF_ART` |
- Текущий объём: 44237 строк данных, дубликаты (одинаковый `name`+`type` в разных
  строках) допустимы и все сохраняются — маппинг идёт 1 строка → 1 объект.

### Решения пользователя
1. Конвертировать **все** строки (44237), без лимита.
2. Выходной формат — **строго 15 ключей** как в `samples/sample200.jsonl`;
   поле `count` из TSV в выход **не включается**.

## Processing (алгоритм)

1. Открыть входной TSV (UTF-8), прочитать все физические строки.
2. Пропустить заголовок (первая строка). Пустые физические строки (0 встречено,
   но защита) — пропускаются. Любая непустая строка с числом полей ≠ 4 — ошибка
   `ValueError` с номером строки (жёсткий фейл, без тихого пропуска).
3. Для каждой строки данных построить объект с ровно 15 ключами, в порядке из
   `samples/sample200.jsonl`:
   | Ключ выхода | Значение |
   |---|---|
   | `table_id` | `""` |
   | `question_id` | `""` |
   | `cell_value` | `name` (как есть, с кавычками) |
   | `column_header` | `""` |
   | `row_context` | `{}` (пустой dict — тип как в sample200) |
   | `table_caption_or_title` | `""` |
   | `page_title` | `""` |
   | `page_url` | `""` |
   | `table_index` | `""` |
   | `question_context` | `""` |
   | `candidate_type` | `type` |
   | `source_location` | `""` |
   | `ner_tags` | `all_types`.split("|"), **отсортированный** список (как `sorted(...)` в build_sample.py; пустые сегменты отбрасываются) |
   | `example_id` | `e` + номер строки данных, zero-padded до общей ширины: `f"e{i+1:0{width}d}"`, где `width = max(3, len(str(n)))` (для n=44237 → 5 цифр: `e00001`…) |
   | `subset` | `"dev"` для первых 20 строк, `"eval"` для всех остальных (конвенция sample200: dev e001–e020 / eval e021–e200) |
4. Сериализовать каждый объект `json.dumps(obj, ensure_ascii=False)`, одну строку на
   объект, записать в выходной файл в UTF-8.
5. Вывести в stdout сводку: количество строк, первый/последний `example_id`,
   распределение `subset`.

Порядок объектов в выходном файле совпадает с порядком строк во входном файле.

## Output

### Файл-назначение: `samples/sample200.jsonl` (по умолчанию)
- JSONL, UTF-8, LF; каждая строка — компактный JSON-объект с 15 ключами в порядке,
  указанном в Processing.
- Количество строк = количеству строк данных во входе (сейчас 44237).
- `example_id` уникальны, лексикографическая сортировка совпадает с порядком файла
  (zero-padding до постоянной ширины).
- Code 0 при успехе; ненулевой код и сообщение об ошибке в stderr при:
  - неверном заголовке / отсутствии файла входа → код 2;
  - строке с числом полей ≠ 4 → `ValueError`, код 1.

### CLI
```
python3 scripts/entities_to_sample200.py [INPUT_TSV] [OUTPUT_JSONL]
```
- `INPUT_TSV` — по умолчанию `samples/entities.tsv`;
- `OUTPUT_JSONL` — по умолчанию `samples/sample200.jsonl`.

## Data Flow

```
samples/entities.tsv ──read──▶ entities_to_sample200.py ──write──▶ samples/sample200.jsonl
                                      │
                                      └──(stdout: сводка)──▶ консоль
```
Затрагиваются только два указанных файла. Другие сервисы, хранилища, API, LLM — не
затрагиваются. По завершении конвертации полученный JSONL пригоден для `python3
scripts/exp2_wikidata.py` без изменений.

## Error Handling

| Failure mode | Поведение |
|---|---|
| Входной файл не существует | `FileNotFoundError` → сообщение в stderr, exit code 2 |
| Заголовок ≠ `name\ttype\tcount\tall_types` | `ValueError` с фактическим заголовком → stderr, exit code 1 |
| Непустая строка с полями ≠ 4 | `ValueError` с номером физической строки → stderr, exit code 1 (жёсткий фейл) |
| Пустая физическая строка | пропускается (допустимо) |
| Ошибка записи выхода | исключение с propagate, exit code 1 |

## Testing

Контейнерируемые проверки (реализуются вручную при верификации, `pytest` в репо нет):

1. **Полнота**: выход содержит 44237 строк ≥ 1 JSON-объект на строку; каждый объект
   парсится `json.loads` без ошибок.
2. **Схема**: у каждого объекта ровно 15 ключей, порядок ключей =
   `['table_id','question_id','cell_value','column_header','row_context',
    'table_caption_or_title','page_title','page_url','table_index',
    'question_context','candidate_type','source_location','ner_tags',
    'example_id','subset']`.
3. **Сохранение кавычек**: строка `"That Girl" (with Shaggy)` присутствует в выходе
   с `cell_value` = `"That Girl" (with Shaggy)` (числительные кавычки сохранены).
4. **1:1 маппинг**: количество выходных строк = количеству непустых не-заголовочных
   строк входа; дубликаты name+type сохранены все.
5. **ner_tags**: строка `PERSON|WORK_OF_ART` → `["PERSON","WORK_OF_ART"]` (sorted);
   однотипные — `["ORG"]`.
6. **ID**: `example_id[0] == "e00001"`, `example_id[-1] == "e44237"`, все уникальны,
   длина постоянна.
7. **subset**: первые 20 строк — `"dev"`, остальные — `"eval"`.
8. **Безопасность добавлений**: при прогоне на входе с одной тестовой строкой
   (`name=Test\ttype=PERSON\tcount=1\tall_types=PERSON|ORG`) выход содержит 1 объект
   с `cell_value="Test"`, `ner_tags=["ORG","PERSON"]`, `subset="dev"`.
9. **Отсутствие лишних ключей**: ни в одном объекте нет ключа `count`.

## Exceptions

- Решения пользователя от 2026-09-21: (1) все строки, (2) строго 15 ключей без
  `count`. Оба зафиксированы в «Input» — это осознанное отклонение от возможных
  более «богатых» схем (потеря `count` принята пользователем осознанно).
- Чтение TSV без CSV-quoting — не баг, а требование (иначе теряются кавычки в
  `name`, проверено эмпирически).

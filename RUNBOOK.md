# RUNBOOK: параллельный прогон exp2_wikidata по 6 частям

Инструкция по разделению `samples/sample200.jsonl` (44237 записей) на 6 частей
и параллельному запуску `scripts/exp2_wikidata.py` по частям с 6 машин так,
чтобы не упереться в лимит Wikimedia (200 req/min на один внешний IP).

Связанные артефакты:
- сплиттер: `scripts/split_sample.py` (спецификация: `specs/split_sample.md`);
- CLI-расширение exp2: `--input PATH` и `--cache-name NAME`.

---

## 0. Коротко

```bash
# 1. Один раз дома: разделить выборку на 6 частей
python3 scripts/split_sample.py            # -> samples/sample200_part1..6.jsonl

# 2. Скопировать репозиторий на 6 машин (каждая получает свою часть).
#    На машине K (K = 1..6):
python3 scripts/exp2_wikidata.py --workers 3 --rpm 200 \
    --input samples/sample200_partK.jsonl \
    --cache-name wikidata_partK

# 3. После прогона на машине K переименовать результаты:
mv results/exp2_wikidata.jsonl       results/exp2_wikidata_partK.jsonl
mv results/exp2_wikidata_stats.json  results/exp2_wikidata_partK_stats.json
```

Оценка: часть ≈ 7373 ячейки × 2–3 запроса ≈ 17–22 тыс. запросов → **1,5–2 часа
на машину** при 200 rpm; суммарно ~6× быстрее полного последовательного прогона
(≈8–9 часов на одной машине).

## 1. Установка

Зависимости: только Python 3 (стандартная библиотека `urllib`). venv не нужен,
`tqdm` опционален (без него вместо прогресс-бара будут текстовые строки).

```bash
# на каждой из 6 машин
git clone <repo> wtq_entity_research && cd wtq_entity_research
# или: rsync -a --exclude cache/ --exclude results/ <repo>/ .

# кэш создастся сам, но можно гарантировать каталог заранее:
mkdir -p cache
```

Примечание: `cache/` в `.gitignore`, поэтому при клоне каталог пустой — это
нормально, части выборки непересекающиеся, кэши между машинами не должны
пересекаться по содержимому.

## 3. Запуск одной части

На машине **K** (K = 1..6) — команда из раздела 0. Параметры:

- `--workers 3` — пул потоков (Wikimedia разрешает до 3 конкурентных запросов
  неавторизованному клиенту; скорость ограничивается `--rpm`, не потоками);
- `--rpm 200` — потолок на один внешний IP (см. раздел 4);
- `--input` — ваша часть;
- `--cache-name wikidata_partK` — свой кэш и свой `flock`-лок на часть. Без
  этого любые две машины на общей файловой системе (NFS/общий каталог)
  блокируют друг друга локом `cache/wikidata.lock` и затирают общий кэш.

После прогона переименуйте результаты, иначе следующая часть перезапишет
`results/exp2_wikidata.jsonl` (имя не зависит от входного файла):

```bash
mv results/exp2_wikidata.jsonl       results/exp2_wikidata_partK.jsonl
mv results/exp2_wikidata_stats.json  results/exp2_wikidata_partK_stats.json
```

Замечание для общей файловой системы (NFS): используйте отдельные копии
репозитория на машину (разные каталоги/работы), а не один общий каталог
`results/` — иначе прогоны затирают результаты друг друга.

---

## 4. Что менять от запуска к запуску (анти-бан)

Ключевой факт (docstring `scripts/exp2_wikidata.py`): лимит Wikimedia для
неавторизованного клиента — **200 req/min на один внешний IP**, общий счётчик
на все хосты (wikidata.org + en.wikipedia.org). Из шести запусков менять нужно
ровно три параметра:

1. **`--input samples/sample200_partK.jsonl`** — каждая машина гонит только
   свою непересекающуюся часть. 6 внешних IP × 200 rpm = 1200 rpm суммарно без
   нарушения лимита на каждом IP — это и есть ускорение в 6 раз.
2. **`--cache-name wikidata_partK`** — изоляция кэша и лока по частям
   (обязательно при общем шаринге файловой системы).
3. **`--rpm` и распределение по внешним IP** — главный анти-бан фактор:

   - **Разные внешние IP** у машин (разные сети/провайдеры): `--rpm 200`
     (или 170–190 с запасом).
   - **Две и более машин за одним NAT/корпоративным шлюзом**: у них один
     внешний IP и общий лимит — делите 200 на число машин за этим IP
     (2 машины → `--rpm 90–100` на каждой). Иначе 400 rpm с одного IP → 429
     и блок.

Прочие правила:

- Стартуйте машины с разницей 1–2 минуты — удобнее диагностировать, кто из
  получающих 429 виноват.
- Не меняйте User-Agent (в `scripts/common.py` уже контакт исследователя) —
  без корректного UA Wikimedia блокирует запросы.
- `maxlag=5` уже отправляется на каждый запрос — API тормозит прогон вместо
  ошибок при высокой нагрузке на реплики.
- Не синхронизируйте `cache/` между машинами во время прогона; результаты
  собирайте после завершения.

## 5. Проверка: видит ли сервис разные внешние IP

Wikimedia API не раскрывает клиентский IP в ответах, поэтому проверка
двухуровневая.

**Прямая (эхо-сервисы)** — на каждой машине:

```bash
curl -s https://api.ipify.org; echo
curl -s https://ipinfo.io/ip; echo    # сверка вторым сервисом
```

6 различных адресов → машины выходят в интернет через разные егресс-IP, и
Wikimedia трактует их как независимых клиентов. Совпавшие адреса → машины
**неотличимы** для сервиса (ipify показывает тот же адрес NAT, через который
ходит `urllib`), тогда делите `--rpm` как в разделе 4.

**Поведенческая (косвенная)** — запустить все 6 машин на `--rpm 200`
одновременно. Отсутствие роста 429 и интервала в течение первого часа-двух —
сервис видит машины как независимых клиентов. Появление 429 даже после
снижения rpm на каждой → часть машин делит IP: повторить проверку
`api.ipify.org`, перераспределить rpm.

## 6. Диагностика блокировок

Признаки в прогресс-баре (постфикс `rpm/interval/errors`) и в stats:

- `errors` растёт, `interval` стремится к 4.00 s — IP перегружен (rate limit);
- HTTP 429 с `Retry-After` — rate limit (скрипт сам делает backoff 3–6–12 s);
- HTTP 403 / капча / «IP blocked» — уже IP-блок;
- записи `__error__` в кэше — такие URL перезапрашиваются при следующем прогоне.

Что делать при блокировке:

1. Остановить все машины с подозрительного IP;
2. подождать (обычно достаточно от минут до пары часов);
3. перепроверить внешний IP (`ipify`), при совпадении — перераспределить rpm;
4. снизить `--rpm` на общих IP;
5. перезапустить машины этого IP (прогон продолжается: результаты кэшируются
   на диске каждые ~2–5 с).
